# 001 · Plan Audit — Factory vs ENRICHMENT_MASTER_PLAN

Date: 2026-10-01. Read-only audit of `factory/` (Python engine) + `api/` + `db/` against
`docs/ENRICHMENT_MASTER_PLAN.md`. Dream-team-stack reference: **`docs/DREAM_TEAM_STACK.md` does
not exist** — used `docs/decisions/002-providers.md` instead (as instructed).

Verdict in one line: the backbone (data model, state machine, queue, treasury primitives, provider
adapters, department layout) is built and coherent. What is missing is the **wiring that makes it
true**: the learning loop has no data producers, the app still reads the legacy flat `leads` table,
three web handlers call an LLM in the request path, and the paid-tier cost gate is bypassed.

## 1. North Star check (plan §1)

**Rule 1 — Zero marginal human hours → PARTIAL.** The factory pipeline is fully autonomous and
queue-driven: `run_nightly.run()` does discovery → enqueue → drain → reports with no per-lead human
step (`factory/run_nightly.py:9-28`). No human-per-client step inside the factory. The remaining
human touch is one-time per client: ICP is hand-authored JSON in `clients.icp_config` (no self-serve
onboarding; `docs/decisions/001-data-model.md:52-54`), and provider keys/caps are set by hand
(`factory/DEPLOY.md:29-33`). Actual sending is human by design (CLAUDE.md), not a bug.

**Rule 2 — Smarter with every client (cross-client learning) → PARTIAL.** Shared global pool and
dedupe are real: `companies`/`contacts` are global with a `dedupe_key`
(`db/002-factory-schema.sql:20-35`), discovery dedupes by it (`factory/workers/discovery.py:37-45`),
and the **shared findings board is written** by `site_enrich`/`gemini`
(`factory/providers/site_enrich.py:69-73`, `factory/providers/gemini.py:40-41`). BUT the learning
loop is **inert**: `factory/workers/learning.py` only *reads* `strategy_runs` and
`engagement_events`; **no worker writes either table** (grep confirms the only reference is
learning.py). So strategy scoring and the north-star "replies per 100" aggregate over empty tables,
and `enrichment_findings.strategy_id` is never set. No strategy-level cross-client learning exists yet.

**Rule 3 — Cost-bounded; every external call via adapter + `cost_ledger` + `can_spend` FIRST →
PARTIAL.** Paid data APIs are correct: `apollo.py:16-27`, `hunter.py:24-33`, `prospeo.py:14-25`,
`serper.py:17-27` all call `budget.can_spend()` **before** the call and `log_cost()` after.
Violations:
- **`factory/providers/cheap_llm.py:42-55`** — the LLM router logs cost after but **never calls
  `can_spend` before** the call. The Composer runs through this premium lane
  (`factory/workers/composer.py:96`), so it spends LLM budget with no gate.
- **`api/_lib/llm.js:10-27`** — the web LLM path calls Gemini directly with **no `cost_ledger`
  logging and no `can_spend`**; Treasury is blind to all app-side LLM spend.
- `factory/providers/google_places.py:44` — the paid Place-Details SKU logs cost but has no
  preceding `can_spend`.

**Rule 4 — App only reads; no scraping/LLM/enrichment in the request path → NO (violated).** Three
handlers make a synchronous LLM call inside the request handler:
- `api/assistant.js:37` (`route(prompt)`)
- `api/classify.js:37` (`route(prompt)`)
- `api/clara.js:51` and `api/clara.js:158` (`route(...)`)

All go through `api/_lib/llm.js` → live Gemini `generateContent`. This is enrichment/LLM in the
user's request path, the explicit prohibition in §1.4 and coding rule 3.

**Rule 5 — Runs without the founder's computer → PARTIAL.** Cloud-ready: `factory/service.py` is an
always-on self-scheduling service and `factory/railway.json` is the Railway deploy config. But it is
**not confirmed deployed/scheduled** — `factory/README.md:63` lists "deploying the scheduler on a
cron" as a *Next* item, and `factory/DEPLOY.md:29-30` asks the founder for Railway access to schedule
it. The old UnaBase engine is paused (`docs/decisions/000-current-state.md:7-8`). So today the
factory runs only when invoked manually.

**Rule 6 — One folder per department, numbers in config, readable → PARTIAL (mostly yes).** Structure
is excellent: `factory/workers/*` one file per department, `factory/providers/*` one per API,
`factory/config/*.json`. Config-driven examples: `factory/config/budgets.json`,
`factory/config/thresholds.json` (scoring weights), `factory/config/capacity.json`. Hardcoded-number
drift: `MAX_CYCLES = 3` (`factory/workers/gates.py:8`), `MAX_ATTEMPTS = 5`
(`factory/packages/queue.py:7`), the LLM model ladder + per-call cost estimates
(`factory/providers/cheap_llm.py:10-21`), and `tier2_threshold` lives in config
(`thresholds.json:4`) but is **never read** (see §8).

## 3. Data model (plan §9)

DDL: `db/002-factory-schema.sql` (+ `db/003-composed-column.sql` adds `client_leads.composed`).

**Present** (16 tables): `companies`, `contacts`, `enrichment_findings`, `assets`, `client_leads`,
`gate_results`, `engagement_events`, `reports`, `strategies`, `strategy_runs`, `templates`,
`template_stats`, `cost_ledger`, `provider_accounts`, `job_log`, plus `signals` (dream-team extra,
not in §9). `clients` pre-exists in prod (not in this DDL; used by workers + `auth`).

**Missing / renamed vs §9:**
- `icps` — **missing by design**; folded into `clients.icp_config` JSON, with `client_leads.icp_id`
  reserved for later (`docs/decisions/001-data-model.md:52-54`; column at schema:113).
- `jobs` — renamed to **`job_log`** (`schema:235`); live queue is pgmq per the comments, though the
  pgmq `create` calls are commented out (`schema:302-306`) and the code actually uses `job_log` +
  `claim_job()`.

**Table mixing client-specific and global data → the old flat `leads` table.** It carries company +
contact + `client_id` + score + status + `lead_data` JSONB in one row and is still the live table the
app reads (`api/leads.js:24`). This is exactly the row the plan wants split into
global `companies`/`contacts` + per-client `client_leads`; the split schema exists but the app was
never cut over (§8.8). `cost_ledger` intentionally carries both `client_id` and global `company_id`
(ledger spans both zones) — acceptable, not a mix violation.

## 4. Lead state machine (plan §4)

**Single module owns transitions → YES.** `factory/packages/lead_state.py` is the sole authority:
`ALLOWED` map + `move()` raising `InvalidTransition` (lines 13-53), mirrored by a DB CHECK constraint
(`db/002-factory-schema.sql:128-130`). All workers go through it (`gates.py:35,38,40`,
`scoring.py:64,67,70,72`, `tier2.py:76`, `runner.py:18,24,45`).

**`max_enrichment_cycles` enforced → YES, but hardcoded.** `cycle_count` is incremented on each
re-entry to `T1_ENRICHING` from `GATE_CHECK`/`PARKED` (`lead_state.py:48-49`), and
`gates.py:37` sends a lead to `PARKED` once `cycle_count >= MAX_CYCLES`. The limit is the constant
`MAX_CYCLES = 3` in `gates.py:8`, not the config value the plan names (`max_enrichment_cycles`,
default 3). `thresholds.json` has no such key.

**Can a lead loop between tiers forever today → NO.** The `T1 → … → GATE_CHECK → T1` loop is bounded
by the cycle cap → `PARKED`. The opposite problem exists: `PARKED` is effectively terminal —
`scheduler.tick()` only enqueues `DISCOVERED` leads (`scheduler.py:10`), so although
`PARKED → T1_ENRICHING` is a legal transition, **nothing ever triggers it** (plan §4's "retried when
a new strategy/provider appears" is unimplemented; §8.9).

## 7. Account-based mode

**Not supported. Zero references** to `account_based` / `mode` / account-level tracking anywhere in
`factory/`, `api/`, `db/`, or the app (grep empty).

The data model actively forbids it: `client_leads` has `unique (client_id, company_id)`
(`db/002-factory-schema.sql:122`), i.e. exactly **one lead per company per client**, and each
`client_lead` pins a single `contact_id` (schema:108). `contacts` are per-company and can be many, but
there is no way to run several deliberate contacts at one company for one client, and no account-level
aggregation.

**Where it would plug in:** (a) relax the constraint to `UNIQUE(client_id, company_id, contact_id)`
or introduce an `accounts`/`account_touches` table so multiple contacts per company per client can
coexist; (b) add a `mode: account_based` flag in `clients.icp_config`, read by `discovery.py`
(create one `client_lead` per decision-maker) and `scoring.py`; (c) `tier2.py` would create N
contacts instead of one; (d) `engagement_events` would need per-contact granularity (today it keys to
`client_lead_id`, schema:148).

## 8. Drift (code does what the plan forbids, or plan assumes what code lacks)

1. **LLM in the web request path** — `api/assistant.js:37`, `api/classify.js:37`,
   `api/clara.js:51,158` call Gemini synchronously. Violates §1.4 + coding rule 3.
2. **Web LLM bypasses Treasury** — `api/_lib/llm.js:10-27` logs nothing to `cost_ledger` and never
   calls `can_spend`. Violates coding rules 1–2; all app-side LLM spend is invisible.
3. **`cheap_llm` bypasses `can_spend`** — `factory/providers/cheap_llm.py:42-55` logs cost but has no
   budget check before the call; the Composer spends on the premium lane ungated. Violates coding rule 2.
4. **`max_enrichment_cycles` hardcoded** — `factory/workers/gates.py:8` (`MAX_CYCLES = 3`); plan §4
   wants it in config.
5. **`tier2_threshold` is dead config** — defined at `factory/config/thresholds.json:4` but never
   read. `factory/workers/scoring.py:66` routes `SCORED → T2_ENRICHING` whenever a domain/website
   exists, **ignoring the score**. Plan §D4 entry criteria is `lead_score >= tier2_threshold`. This
   triggers the paid tier regardless of lead value — a direct cost risk.
6. **`claim_job()` RPC not in the repo** — `factory/packages/queue.py:18` calls
   `db.rpc("claim_job")`, and it's described in `DEPLOY.md:16`/`README.md:14`, but its DDL is in **no
   `db/*.sql` file**. The queue depends on an un-versioned DB function.
7. **Learning loop has no producers** — nothing writes `strategy_runs` or `engagement_events`
   (`learning.py` only reads them); `enrichment_findings.strategy_id` is always null. North Star #2 +
   Phase 4 have no data source.
8. **Factory output not wired to the app** — `api/leads.js:24` still reads the legacy flat `leads`
   table; nothing in `api/` reads `reports` or `client_leads`. Plan §1.4/§4 assume the app reads the
   precomputed views the factory produces.
9. **PARKED never retried** — `factory/workers/scheduler.py:10` enqueues only `DISCOVERED`; plan §4's
   "PARKED retried when a new strategy/provider appears" is unimplemented (the transition is legal but
   untriggered).
10. **Per-client/plan + daily budgets not enforced** — `budget.py:3-4` defers per-client budgets;
    `can_spend` checks only the monthly global cap, so `daily_global_spend_cap_usd`
    (`budgets.json:4`) and the per-plan quotas (`budgets.json:8-12`) are inert.
11. **Paid Place-Details ungated** — `factory/providers/google_places.py:44` logs cost without a
    preceding `can_spend`.
12. **Doc/state inconsistency** — `README.md:55-59` says the schema is applied and "Phase 1 DONE …
    1,128 companies + 2,004 contacts migrated", while `docs/decisions/001-data-model.md:3` and the
    schema header say "design only, NOT yet applied". `003-composed-column.sql:1` says applied to
    prod. Repo alone can't confirm the live DB state.
13. **No per-timezone 8am reports** — plan §D9/D0 want reports at 08:00 in each client's timezone;
    `factory/service.py:36` fires at one `FACTORY_RUN_HOUR_UTC` for everyone and
    `reports.build_all()` ignores client timezone.

## Three highest-leverage next tasks

1. **Close the cost-safety holes (≈3h).** Make `tier2_threshold` real in `scoring.py` (only escalate
   to `T2_ENRICHING` when `score >= tier2_threshold`), add a `can_spend` gate at the top of
   `cheap_llm.generate()`, and add `can_spend` + `log_cost` to `api/_lib/llm.js`. This stops the paid
   tier and all LLM spend from running ungated — the fastest risk reduction, directly on North Star #3.

2. **Wire the learning producers (≈6–8h).** Write a `strategy_runs` row per enrichment pass (tag
   findings with a `strategy_id`) and translate the app's existing status changes
   (`mark-sent` / `notes` / `status_history`) into `engagement_events`. This turns `learning.py` from
   an aggregate-over-empty into a live loop and is the only thing that makes North Star #2 ("smarter
   with every client") and Phase 4 true.

3. **Cut the app over to factory output (≈6h).** Point the client surface at the precomputed `reports`
   (or a `client_leads`-backed view) instead of the legacy flat `leads` table (`api/leads.js`), and
   move the three in-request LLM handlers (assistant/classify/clara) to a queued/precomputed path.
   This satisfies §1.4 ("app only reads, fast") and finally connects the built factory to what clients
   see.
